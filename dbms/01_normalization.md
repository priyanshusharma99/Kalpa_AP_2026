# Kalpa (Collaborative Design Tool) — Database Normalization

**Project Name:** Kalpa (Collaborative Design Platform / Figma Clone)  
**Document:** `dbms/01_normalization.md`  
**Purpose:** Formal database normalization analysis from Unnormalized Form (UNF) through 1NF, 2NF, 3NF, and BCNF, including data source architecture and integrity constraints.

---

## 1. System Overview & Architecture

### 1.1 Core Domain
**Kalpa** is a real-time collaborative vector graphics and design tool inspired by Figma. Multiple users can concurrently work on shared design canvases, create and manipulate vector shapes, draw freehand, upload images, leave pinned comments on canvas coordinates, and manage team permissions.

### 1.2 Data Storage Architecture: PostgreSQL vs. Liveblocks
In collaborative canvas tools, real-time collaboration and persistent storage serve distinct roles:

| Aspect | PostgreSQL (Authoritative System of Record) | Liveblocks (Real-Time Ephemeral Sync) |
| :--- | :--- | :--- |
| **Role** | **Authoritative Persistent Database** | **Real-Time Collaboration Engine** |
| **Data Managed** | Users, Projects, Permissions, Persisted Shapes, Comment Pins, Replies, Audit History. | Live user cursors, active cursor chat messages, live floating emoji reactions, active dragging states. |
| **Storage Nature** | Durable ACID disk storage with foreign key constraints. | In-memory WebSocket CRDT room state with periodic room storage snapshots. |
| **Conflict Handling** | ACID transactions, foreign keys, and unique constraints. | Last-Write-Wins (LWW) / CRDT resolution in active sessions, flushed to PostgreSQL upon save / debounce. |

*(Note: Liveblocks coordinates active client-side WebSocket synchronization, while the PostgreSQL schema provides durable persistence and relational constraints).*

## 2. Step 0: Unnormalized Form (UNF)

In an unnormalized state, a single flattened record represents an entire design canvas file with nested collections, repeating groups, and multi-valued attributes.

### Unnormalized Relation: `UNF_PROJECT`
```text
UNF_PROJECT(
    project_id,
    project_title,
    canvas_width,
    canvas_height,
    canvas_bg_color,
    owner_id,
    owner_name,
    owner_email,
    owner_role,
    collaborators: [
        { user_id, user_name, user_email, role_name, access_level_desc }
    ],
    elements: [
        { element_id, shape_type, pos_x, pos_y, width, height, scale_x, scale_y, rotation, opacity, 
          fill_color, stroke_color, stroke_width, z_index, text_content, image_url, custom_properties, 
          creator_id, creator_name }
    ],
    comments: [
        { comment_id, pin_x, pin_y, status, creator_id, creator_name, 
          replies: [
              { reply_id, author_id, author_name, message_text, created_at }
          ]
        }
    ]
)
```

### Anomalies in UNF:
- **Insertion Anomaly:** A new user cannot be created in the system without creating or being assigned to an existing project. A shape definition or comment thread cannot exist without an overarching project.
- **Update Anomaly:** If a user updates their email or username, every occurrence in `collaborators`, `elements`, and `comments` across all projects must be updated. Any missed row produces inconsistent user data.
- **Deletion Anomaly:** If a project is deleted, all comments, collaborator links, and element creator profiles stored solely inside the project record are destroyed.

## 3. First Normal Form (1NF)

### 1NF Criteria:
1. Every column contains **atomic** (indivisible) values. No grouped or composite attributes.
2. There are **no repeating groups** or nested arrays.
3. Each record is uniquely identified by a defined Primary Key or Composite Key.

### Transformation to 1NF:
Repeating groups (`collaborators`, `elements`, `comments`, `replies`) are extracted into discrete flat tabular rows. Primary keys are defined as `VARCHAR(64)` identifiers (which store unique string identifiers generated by the application).

#### Relation 1: `PROJECT_1NF`
- **Attributes:** `project_id`, `project_title`, `canvas_width`, `canvas_height`, `canvas_bg_color`, `owner_id`, `owner_name`, `owner_email`
- **Primary Key:** `{project_id}` (Single-attribute `VARCHAR(64)`)

#### Relation 2: `PROJECT_COLLABORATOR_1NF`
- **Attributes:** `project_id`, `user_id`, `user_name`, `user_email`, `role_name`, `access_level_desc`, `joined_at`
- **Primary Key:** `{project_id, user_id}` (Composite Key: `VARCHAR(64), VARCHAR(64)`)

#### Relation 3: `CANVAS_ELEMENT_1NF`
- **Attributes:** `element_id`, `project_id`, `shape_type`, `pos_x`, `pos_y`, `width`, `height`, `scale_x`, `scale_y`, `rotation`, `opacity`, `fill_color`, `stroke_color`, `stroke_width`, `z_index`, `text_content`, `image_url`, `custom_properties`, `creator_id`, `creator_name`, `created_at`, `updated_at`
- **Primary Key:** `{element_id}` (Single-attribute `VARCHAR(64)`)

#### Relation 4: `COMMENT_PIN_1NF`
- **Attributes:** `comment_id`, `project_id`, `pin_x`, `pin_y`, `status`, `creator_id`, `creator_name`, `created_at`
- **Primary Key:** `{comment_id}` (Single-attribute `VARCHAR(64)`)

#### Relation 5: `COMMENT_REPLY_1NF`
- **Attributes:** `reply_id`, `comment_id`, `author_id`, `author_name`, `message_text`, `created_at`
- **Primary Key:** `{reply_id}` (Single-attribute `VARCHAR(64)`)

## 4. Second Normal Form (2NF)

### 2NF Criteria:
1. The relation must be in **1NF**.
2. **No Partial Functional Dependencies:** Every non-prime attribute must be fully functionally dependent on the entire candidate key.
   > **Theoretical Rule:** Partial dependency can *only* occur when a candidate key is **composite** (consisting of two or more attributes). A non-prime attribute cannot depend on a proper subset of a composite candidate key. If a candidate key is a single attribute, the relation is automatically in 2NF.

### Analysis of 1NF Relations for 2NF:

1. **`PROJECT_COLLABORATOR_1NF` (Has Composite Key: `{project_id, user_id}`):**
   - Candidate Key: `{project_id, user_id}`
   - Functional Dependencies:
     - `{project_id, user_id} -> role_name, access_level_desc, joined_at` *(Full Dependency on entire key)*
     - `user_id -> user_name, user_email` *(Partial Dependency on proper subset `user_id`)*
   - **Violation:** `user_name` and `user_email` depend only on `user_id`, violating 2NF.
   - **Resolution:** Decompose and extract user identity attributes into a dedicated `USER` relation:
     - `USER(user_id [PK], user_name, user_email)`
     - `PROJECT_COLLABORATOR(project_id [PK, FK], user_id [PK, FK], role_name, access_level_desc, joined_at)`

2. **`CANVAS_ELEMENT_1NF`, `COMMENT_PIN_1NF`, `COMMENT_REPLY_1NF`:**
   - Candidate Keys: `{element_id}`, `{comment_id}`, `{reply_id}` respectively (each is a single-attribute `VARCHAR(64)`).
   - Because their primary keys consist of a single column, they have no proper subsets. Therefore, they **trivially satisfy 2NF** (no partial dependencies exist).
   - *Note on `creator_id -> creator_name`:* In these tables, `creator_id` is a non-prime attribute determining another non-prime attribute (`creator_name`). Because `creator_id` is not part of a composite key, this is a **Transitive Dependency** ($element\_id \to creator\_id \to creator\_name$), which is formally resolved in **3NF**, not 2NF.

### Resulting 2NF Relations:
1. `USER_2NF(user_id [PK], user_name, user_email)`
2. `PROJECT_2NF(project_id [PK], project_title, canvas_width, canvas_height, canvas_bg_color, owner_id [FK], created_at, updated_at)`
3. `PROJECT_COLLABORATOR_2NF(project_id [PK, FK], user_id [PK, FK], role_name, access_level_desc, joined_at)`
4. `CANVAS_ELEMENT_2NF(element_id [PK], project_id [FK], shape_type, pos_x, pos_y, width, height, scale_x, scale_y, rotation, opacity, fill_color, stroke_color, stroke_width, z_index, text_content, image_url, custom_properties, creator_id [FK], creator_name, created_at, updated_at)`
5. `COMMENT_PIN_2NF(comment_id [PK], project_id [FK], pin_x, pin_y, status, creator_id [FK], creator_name, created_at)`
6. `COMMENT_REPLY_2NF(reply_id [PK], comment_id [FK], author_id [FK], author_name, message_text, created_at)`

## 5. Third Normal Form (3NF)

### 3NF Criteria:
1. The relation must be in **2NF**.
2. **No Transitive Dependencies:** No non-prime attribute is transitively dependent on any candidate key (i.e., for every non-trivial functional dependency $X \to Y$, either $X$ is a superkey or $Y$ is a prime attribute).

### Analysis of Transitive Dependencies:

1. **In `CANVAS_ELEMENT_2NF`, `COMMENT_PIN_2NF`, and `COMMENT_REPLY_2NF`:**
   - Dependencies:
     - `element_id -> creator_id` and `creator_id -> creator_name`
     - `comment_id -> creator_id` and `creator_id -> creator_name`
     - `reply_id -> author_id` and `author_id -> author_name`
   - In each case, `creator_id` / `author_id` is a non-prime attribute determining another non-prime attribute (`creator_name` / `author_name`).
   - **Resolution:** Remove `creator_name` and `author_name`. Retain only the foreign keys `creator_id` and `author_id` referencing `USER(user_id)`.

2. **In `PROJECT_COLLABORATOR_2NF`:**
   - Primary Key: `{project_id, user_id}`
   - Dependencies:
     - `{project_id, user_id} -> role_name`
     - `role_name -> access_level_desc, can_edit, can_comment, can_share`
   - Non-prime attribute `access_level_desc` depends on `role_name`, which is a non-prime attribute (Transitive Dependency: $PK \to role\_name \to access\_level\_desc$).
   - **Resolution:** Extract role permissions into an independent lookup relation `ROLE_PERMISSIONS(role_name [PK], access_level_desc, can_edit, can_comment, can_share)`.

### Owner-Collaborator Invariant Enforcement:
- `PROJECTS.owner_id` explicitly references `USERS(user_id)`.
- The business invariant that **every project has exactly one owner collaborator matching `projects.owner_id`** is enforced by:
  1. **Partial Unique Index:** `CREATE UNIQUE INDEX uq_project_single_owner ON project_collaborators (project_id) WHERE role_name = 'owner';` guarantees that at most one collaborator can hold the `'owner'` role per project.
  2. **Sync Trigger (`trg_projects_owner_sync`):** When a project is created, the owner is inserted as an `'owner'` collaborator. When ownership is transferred (`owner_id` changes), the new owner is registered as `'owner'` and the previous owner is automatically demoted to `'editor'`.
  3. **Protection Trigger (`trg_protect_project_owner`):** 
     - Rejects any INSERT or UPDATE assigning `role_name = 'owner'` to any user other than `projects.owner_id`.
     - Rejects any direct UPDATE attempting to demote, reassign, or alter the `user_id` or `project_id` of the active owner row in `project_collaborators`.
     - Rejects direct DELETE of the owner row from `project_collaborators` while the project still exists, while allowing cascading deletes when the parent project or user is removed.

## 6. Boyce-Codd Normal Form (BCNF)

### BCNF Criteria:
1. The relation must be in **3NF**.
2. For every non-trivial functional dependency $X \to Y$, the determinant $X$ **must be a Super Key**.

### Functional Dependencies (FDs) Verification:

#### 1. `USER`
- Determinants & FDs:
  - `user_id -> user_name, user_email, avatar_url, created_at, updated_at` (`user_id` is PK / Super Key)
  - `user_email -> user_id, user_name, avatar_url, created_at, updated_at` (`user_email` is Unique Candidate Key)
- **Status:** **Satisfies BCNF** $\checkmark$

#### 2. `ROLE_PERMISSIONS`
- Determinants & FDs:
  - `role_name -> access_level_desc, can_edit, can_comment, can_share`
  - `role_name` is PK / Super Key.
- **Status:** **Satisfies BCNF** $\checkmark$

#### 3. `PROJECTS`
- Determinants & FDs:
  - `project_id -> project_title, canvas_width, canvas_height, canvas_bg_color, owner_id, created_at, updated_at`
  - `project_id` is PK / Super Key.
- **Status:** **Satisfies BCNF** $\checkmark$

#### 4. `PROJECT_COLLABORATORS`
- Determinants & FDs:
  - `{project_id, user_id} -> role_name, joined_at`
  - Determinant `{project_id, user_id}` is Composite PK / Super Key.
- **Status:** **Satisfies BCNF** $\checkmark$

#### 5. `CANVAS_ELEMENTS`
- Determinants & FDs:
  - `element_id -> project_id, shape_type, pos_x, pos_y, width, height, scale_x, scale_y, rotation, opacity, fill_color, stroke_color, stroke_width, z_index, text_content, image_url, custom_properties, creator_id, created_at, updated_at`
  - `element_id` is `VARCHAR(64)` PK / Super Key.
- **Status:** **Satisfies BCNF** $\checkmark$

#### 6. `COMMENT_PINS`
- Determinants & FDs:
  - `comment_id -> project_id, pin_x, pin_y, status, creator_id, created_at`
  - `comment_id` is `VARCHAR(64)` PK / Super Key.
- **Status:** **Satisfies BCNF** $\checkmark$

#### 7. `COMMENT_REPLIES`
- Determinants & FDs:
  - `reply_id -> comment_id, author_id, message_text, created_at`
  - `reply_id` is `VARCHAR(64)` PK / Super Key.
- **Status:** **Satisfies BCNF** $\checkmark$

All relations satisfy the criteria of **BCNF** with lossless decomposition and dependency preservation.

## 7. Integrity Constraints & Foreign Key Rules

| Foreign Key Relationship | Referenced Table | On Delete Rule | On Update Rule | Architectural Rationale |
| :--- | :--- | :--- | :--- | :--- |
| `projects.owner_id` | `users.user_id` | `CASCADE` | `NO ACTION` (default) | If owner account is deleted, personal projects cascade. |
| `project_collaborators.project_id` | `projects.project_id` | `CASCADE` | `NO ACTION` (default) | Memberships wiped upon project deletion. |
| `project_collaborators.user_id` | `users.user_id` | `CASCADE` | `NO ACTION` (default) | Removing a user account removes their collaboration memberships. |
| `project_collaborators.role_name` | `role_permissions.role_name`| `RESTRICT` | `CASCADE` | Role rename cascades; cannot delete role while users hold it. |
| `canvas_elements.project_id` | `projects.project_id` | `CASCADE` | `NO ACTION` (default) | Canvas shapes belong strictly to a project; deleted with project. |
| `canvas_elements.creator_id` | `users.user_id` | `SET NULL` | `NO ACTION` (default) | Shapes remain on canvas even if creator account is deleted. |
| `comment_pins.project_id` | `projects.project_id` | `CASCADE` | `NO ACTION` (default) | Comments belong to the canvas; deleted with project. |
| `comment_pins.creator_id` | `users.user_id` | `SET NULL` | `NO ACTION` (default) | Thread pins persist with author set to null if author leaves. |
| `comment_replies.comment_id` | `comment_pins.comment_id` | `CASCADE` | `NO ACTION` (default) | If comment pin is removed, reply messages are cleaned up. |
| `comment_replies.author_id` | `users.user_id` | `SET NULL` | `NO ACTION` (default) | Reply text remains in discussion history if author leaves. |

### Domain Value Constraints:
- `canvas_width`, `canvas_height`: `CHECK (canvas_width >= 100 AND canvas_width <= 10000)`
- `shape_type`: `CHECK (shape_type IN ('rect', 'circle', 'triangle', 'path', 'text', 'image'))`
- `status`: `CHECK (status IN ('open', 'resolved'))`
- `role_name`: `CHECK (role_name IN ('owner', 'editor', 'viewer'))`
- `rotation`: `CHECK (rotation >= 0.00 AND rotation < 360.00)`
- `opacity`: `CHECK (opacity >= 0.00 AND opacity <= 1.00)`
- `scale_x`, `scale_y`: `CHECK (scale_x > 0.00 AND scale_y > 0.00)`
